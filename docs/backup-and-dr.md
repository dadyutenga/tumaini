# Backup, Disaster Recovery & Business Continuity Runbook

This runbook defines recovery objectives, backup schedules, encryption, offsite storage, restoration testing, and rollback procedures for Tumaini BMS.

## 1. Recovery Objectives

| Metric | Target | Mechanism |
| --- | --- | --- |
| **RPO** (Recovery Point Objective) | **≤ 24 hours** (nightly) / **≤ 15 minutes** (with optional WAL archiving to object storage) | Automated nightly encrypted `pg_dump` at `01:15` server time + pre-deploy backup before every release |
| **RTO** (Recovery Time Objective) | **≤ 30 minutes** | Automated restore via `deploy/restore-verify.sh` / `pg_restore` and container redeployment via `deploy/deploy.sh` |

## 2. Backup Schedule & Retention Policy

| Backup Type | Schedule | Local Retention (`/var/backups/tumaini`) | Offsite Retention (`BACKUP_UPLOAD_CMD`) |
| --- | --- | --- | --- |
| Nightly automated DB dump | Daily at `01:15` via `/etc/cron.d/tumaini-backup` (`deploy/backup-prod.sh nightly`) | 30 days (`BACKUP_KEEP_DAYS=30`) | 90 days daily + 12 months monthly snapshots (object storage lifecycle rule) |
| Pre-deploy snapshot | Before every release via `deploy/deploy.sh` (`deploy/backup-prod.sh predeploy`) | 30 days | Synced immediately via `BACKUP_UPLOAD_CMD` |
| Monthly restore drill | 1st Sunday of every month | Ephemeral DB (`bms_restore_verify_*`) dropped after verification | Verified against latest offsite encrypted dump |

## 3. Backup Encryption & Offsite Storage

- **Encryption at rest**: `deploy/backup-prod.sh` and `deploy/backup.sh` encrypt every PostgreSQL custom-format dump using **AES-256-CBC with PBKDF2-SHA256 (600,000 iterations)** and a random salt (`openssl enc -aes-256-cbc -pbkdf2 -iter 600000 -salt`), generating `<file>.dump.enc` and `<file>.dump.enc.sha256` with `0600` permissions inside a `0700` directory.
- **Strict mode**: Set `BACKUP_REQUIRE_ENCRYPTION=1` in `/opt/tumaini/.env` so backups fail closed if `BACKUP_ENCRYPTION_KEY` is missing.
- **Key custody**: `BACKUP_ENCRYPTION_KEY` is generated by `deploy/server-setup.sh` (`openssl rand -hex 32`) and MUST be backed up in the organization's password manager / KMS separately from both the production host and the offsite backup bucket.
- **Offsite storage**: Configure `BACKUP_UPLOAD_CMD` in `/opt/tumaini/.env` (e.g., `rclone copy "$1" offsite-s3:tumaini-backups/`) so encrypted dumps and `.sha256` manifests leave the production host immediately.

## 4. Monitoring & Backup Failure Alerts

- Both `deploy/backup-prod.sh` and `deploy/backup.sh` register an `ERR` trap that removes partial artifacts, logs a timestamped error to `/var/log/tumaini-backup.log`, and sends a JSON webhook alert to `BACKUP_ALERT_WEBHOOK_URL` (Slack / PagerDuty / Opsgenie / custom alert relay).
- Alerting rule: Trigger a critical alert if no `backup written:` entry appears in `/var/log/tumaini-backup.log` within 26 hours or if any `backup_failed` webhook fires.

## 5. Automated Restore Verification & Post-Recovery Reconciliation

Run the automated verification script against any `.dump` or `.dump.enc` archive without touching the live production database:

```bash
cd /opt/tumaini
./restore-verify.sh /var/backups/tumaini/bms-nightly-YYYYMMDDTHHMMSSZ.dump.enc
```

`restore-verify.sh` automatically:
1. Verifies the `.sha256` checksum.
2. Decrypts the AES-256 archive into a `0600` temporary file.
3. Restores into an isolated ephemeral database (`bms_restore_verify_<pid>`).
4. Verifies **three post-recovery integrity invariants**:
   - **Financial reconciliation**: `app.financial_accounts.current_balance == SUM(app.financial_transactions)` (`0` mismatches).
   - **Inventory reconciliation**: `app.stock_balances.quantity_on_hand == SUM(app.stock_movements)` (`0` mismatches).
   - **Audit trail integrity**: `audit.verify_tenant(id)` reports `0` broken cryptographic hash-chain seals.
5. Drops the ephemeral database and deletes temporary decrypted files.

## 6. Production Disaster Recovery Procedure

1. Provision a clean host (or stop `api` and `web` on the existing host: `docker compose -f docker-compose.prod.yml stop api web`).
2. Fetch the latest encrypted backup + `.sha256` from offsite storage and run `./restore-verify.sh <archive>` first.
3. Decrypt and restore into `bms`:
   ```bash
   set -a; . /opt/tumaini/.env; set +a
   openssl enc -d -aes-256-cbc -pbkdf2 -iter 600000 -in backup.dump.enc -pass env:BACKUP_ENCRYPTION_KEY \
     | docker compose -f docker-compose.prod.yml exec -T postgres pg_restore -U postgres -d bms --clean --if-exists --no-owner
   ```
4. Re-apply login role passwords (`bms_api`, `bms_jobs`) and start the stack via `./deploy.sh <known_good_tag>`.
5. Run post-recovery reconciliation queries (`LedgerBalanceCheck`, `StockRebuildCheck`, `audit.verify_tenant`) and verify `/readyz` returns `200 ok`.

## 7. Application Rollback & Migration Recovery

- **Application rollback**: `deploy/deploy.sh <tag>` records `.deployed_tag` and automatically rolls back `api` and `web` to the previous image tag if health checks fail. Manual rollback:
  ```bash
  cd /opt/tumaini && ./deploy.sh <previous_sha_tag>
  ```
- **Database migrations**: Migrations are **forward-only** (`backend/database/migrations/`). Never edit an applied migration. If a schema release causes an incident:
  1. For backward-compatible issues: roll forward with a new corrective migration (`NNN_*.sql`).
  2. For destructive/unrecoverable schema regressions: stop `api`, restore the `predeploy` encrypted backup taken automatically by `deploy.sh`, and deploy the previous application tag.
